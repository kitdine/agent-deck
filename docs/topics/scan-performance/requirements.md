# Scan performance：先准备数据，再打开界面

状态由 [tasks.md](tasks.md) 管理。本文是 2026-10-22 全 topic 重新设计后的需求边界：
验收指标恢复为设计获批提交 `c376984` 的 P01–P11 原值，此后的全部调整、豁免、撤销与
“按修订条件接受”一律撤回，不再作为任何任务的完成依据。测量方法由
[性能评估](performance-evaluation.md) 的测量契约规定；不可测的指标只能在设计中改方法并经评审，
不得在实现或评审阶段豁免、跳过或改验收条件。

## 第一次使用和以后使用

本机 Codex/Claude 的原始日志、AgentDeck 已整理的数据库、上次界面的保存文件是三件事。
全新安装即使本机日志很多，后两者仍为空，不能靠恢复快照解决第一次等待。

| 用户实际处境 | 第一批如何得到可用数据 | 后续工作 |
| --- | --- | --- |
| 新安装，AgentDeck 库空，本机旧日志很多 | 发现全部来源的 metadata，优先处理今天相关来源；从完整文件上下文算出今天的值并发布 | 继续补历史，其他窗口/字段标为部分或未准备；不等历史完成才显示今天 |
| 已有数据库，今天记录已入库，没有展示保存文件 | 直接查询已提交的今天用量；先供给已准备字段 | 按需准备其他窗口/会话/工作信号；不先重新扫描全部日志或计算90天视图 |
| 已有数据库，今天日志尚未入库 | 已有有效视图先可读；今天新值等待增量导入提交后发布 | 增量导入本身须满足 P10；不能用缓存恢复时间声称最新值实时可用 |
| 有有效的上次展示保存文件 | 校验身份/日期后恢复上次数据 | 后台处理变化；旧值的年龄保持真实。跨天不把昨日值标作今天 |

方案不是“先预先存在缓存才快”。它分别包含首次当天优先、已有库的当天只读准备，
以及上次展示恢复。当天优先在冻结语料上用量与全量一致，但仅靠目录/mtime提示不能证明未来所有输入完整。
第一阶段显示“今天已采集用量 / 历史正在补齐”，全量校对前不承诺所有来源已收齐。

## 目标与用户决定

核心目标：用户点击菜单栏 icon 后，popover 迅速显示能够使用的数据。
性能成功不能用窗口出现、spinner 出现、扫描完成更快或返回空数字替代。
可用数据包含正确的客户端、时段、单位、数据日期和完整性说明，并能切换现有面板。

2026-10-09 用户明确了以下边界：

- 不能把目标划分成“当天优先”与“历史全量优先”；优化对象是打开 popover 后看到数据的体验。
- OTel 是后台实时数据来源，不属于点击打开 popover 的等待路径。
- 后台采集默认随菜单栏 App 运行，退出 App 就停止；独立后台模式另行启用。
  这是生命周期要求，不要求一定新增常驻 Go 进程。当前 macOS App 已常驻。
- CLI 必须一起设计，复用同一套数据、调度和状态契约。
- 必须先评估收益；比较线程、进程、分段统计、近期优先和实时采集，不能持续尝试无收益的代码优化。

2026-10-22 用户决定全 topic 重新设计：

- P01–P11 恢复原值；此前所有豁免、撤销、×1.5 调整、样本数收窄与验收例外撤回。
- 每项指标须有可自动、可复现的产品内起止打点、固定种子生成的夹具、统计口径、
  样本数与机器条件；可测性在设计阶段判定。
- 在现有代码上开发，确认无用的代码、脚本和测量工具在实现中删除。
- 证据只进入 Neo4j CEv1 与评审记录，topic 下不再新建 evidence 文件。

输入分类为 `SUFFICIENT`。生产者字段不确定性以能力门禁处理，不假定字段存在。

## 两条路径

| 路径 | 做什么 | 不能等待什么 |
| --- | --- | --- |
| 展示 | 读已校验的内存快照；启动时恢复最后可用的磁盘展示快照；切换预备好的视图 | 文件发现、JSONL 解析、重建、SQL 全表聚合、额度网络调用、OTel 到达、worker 排队 |
| 更新 | App 接收文件变化提示，复用现有单协调者执行有限增量任务；统计提交后发布展示快照；OTel 为独立可选输入 | 界面打开、界面保持可见或消费者逐个消费进度 |

已有数据暂旧不等于不可用。旧数据的日期、来源覆盖和额度 observation 时间必须保留，
不能把打开时间或一次刷新尝试时间改写成数据时间。

记录默认关闭，驱动只编入专用测量构建，不进入发布产物。

## 行为要求

### 展示数据

- 内存命中直接展示；磁盘恢复只在后台读取、解码和准备视图，主线程不读数据库或 JSON。
- 恢复快照必须绑定本机 state root、core/session epoch、受支持 schema/wire、
  实际数据窗口和时区。dirty/revision 变化使它“较旧”，不是自动删除最后可用数据。
- 身份变化、损坏、错误权限、跨 state root、未来 wire/schema 使缓存不可展示；不得绕过已有 schema signal。
- 所有可复用的客户端、时段和面板从同一 publication 中读取。日期失效的 today 不显示昨日数为今日数。
- 无展示缓存但已有数据库时，从已提交记录准备初始展示，不先重扫历史日志。
- 初始只需今天的数据时，不以准备90天、多时段和所有面板为前置条件。
  用量字段可先就绪，项目/工作信号/额度等尚未准备字段显示 unavailable，不能补0或伪造完整。
- 首次当天相关来源包含旧会话今天继续活动的文件，不限今天创建的文件；
  保留累计 token/会话上下文，不从中间随意截取。优先批次是调度范围，不是全球扫描完成证明。
- 首批提交后就能发布，App 不等全局 scan terminal 或 worker 退出才读取。
  后台补历史时保留已验证的首批视图，CLI 全范围请求继续履行自己的完整义务。
- 真正首次导入没有数字时显示准备状态；分段成果可显示为明确的“已采集部分”，
  尚未准备的字段为 unavailable。只有覆盖证明充分时才显示真实零。
- 刷新失败保留有效数据，独立报告实际失败；排队或健康任务持续超过 120 秒不自动变成扫描失败。
- Provider 写操作使用命令执行时的真实配置和前置条件；展示缓存不授权配置修改。

### App 生命周期、事件更新与 CLI

- 一个 state root 一个数据引擎写入协调者；App、CLI、watch 和 collector 不各自扫描/写同一数据。
- 第一阶段 App 启动先恢复展示，再发起一次有限后台更新；点击 icon 不申请扫描任务。
  额外 Go 常驻必须证明持续接收需求或进程启动成本，不能以“App 需要常驻”为理由默认采用。
- App 退出撤销自己的 lease、watch/subscription，App 自己的后台工作在有界 checkpoint 后停止。
  已由 CLI 明确接受的有限任务不被 App 退出取消，可交给按需运行实例续做。
- 若后续采用常驻引擎，无 App lease、独立后台 lease 或有限任务时引擎退出。独立模式只有显式命令启动，
  不默认注册登录项、launch agent 或系统服务。
- 自动更新关闭时不偷偷开启 JSONL 监听或周期采集；开启后以文件事件触发，不等待固定周期。
  启动、唤醒、watcher 报告丢事件时做有限校对。手动、启动时既有有限刷新仍允许；
  显式 OTel 配置控制遥测接收，额度自身调度仍独立。
- CLI 报告默认同步语义保留；`usage stats/summary --no-scan` 不发现或解析日志。
  任意模型/自定义日期查询使用只读已提交数据库，不为凑“快”缩小查询范围。
- 显式扫描有有限 inventory/watermark、幂等 receipt 和独立订阅者取消。实时事件不断到来不会使它永远不结束。

### 采集与统计

- no-op 解析日志正文为零；append 读取新增范围及明确的有限校验锚点。
- 每个来源保留两个 consumer 的解析上下文、newline 边界和版本；不能从文件中段任意开始累计 token。
- 按有界 chunk 读、decode、reduce；全进程内存预算覆盖各阶段与队列，不用 goroutine 数代替预算。
- 来源可并行 reduce，但写入经单一有序写者提交；并行结果与串行 full oracle 逐逻辑行等价。
- 分区统计只重算受影响的时间/客户端/模型/会话集合；非可加指标有自己的集合或 reducer 状态。
- 重建写 shadow derivation，完成并校验后切换 active generation。保护原始 events、凭证、provider、排除配置与源文件。
- 文件 watcher 是提示；journal 丢失、目录变化、rewrite、rename 和 archive move 必须由有限 reconciliation 恢复。

### OTel

- 默认关闭；Settings 或 CLI 只启用 AgentDeck receiver。操作者审阅并自行应用 config preview；
  本轮和自动启动均不修改 Codex 配置。
- 本地接收不代理模型请求，不发送模型请求。只接受允许的模型/token/身份/时间字段，
  prompt、response、tool output、headers 和凭据在落盘前丢弃。
- OTel 到达 → 持久化 → 规范化/去重 → 原子更新统计 → 发布，与 popover 打开完全独立。
- 精确请求/响应身份和 transport 覆盖未通过时保持 `capture_only`，不自动作为完整主来源。
- 不按 timestamp/model/token 相似性猜测 JSONL 与 OTel 属于同一请求。
- 已导出但未留存的数据可能丢失；从启用开始记录覆盖区间、已知断连和历史未知，
  没有记录的历史不能补齐。SSE/WebSocket、重试、失败及中断分别验收。

### 测量能力

- 产品内打点使用单一单调时钟（同机跨进程可比），只记录固定阶段名、数值、机器错误码与
  环境布尔值；不记录路径、会话内容、token 明细以外的数据或凭据。默认关闭，开启不改变行为。
- 测量驱动只在专用测量构建中编入，不进入 Release/安装产物，不请求或修改系统权限。
- 夹具由固定种子生成，不读取真实日志；规模参数来自已记录的脱敏聚合。
- 无效样本不得静默剔除；任何无效样本使该批次无效，修复工具后整批重测。

## 数值验收

这些是产品实现的验收目标。起止打点、刺激、夹具、样本数、统计口径与机器条件由
[性能评估·测量契约](performance-evaluation.md#测量契约) 规定；任何一项不得以“无法测量”豁免。

| ID | 条件与指标 | 目标 |
| --- | --- | --- |
| P01 | App 已运行、有效内存快照；真实 icon click 到首个可读且可交互的数据帧 | p95 ≤200 ms，p99 ≤400 ms；后台全量重建时仍满足 |
| P02 | App 重启、有效磁盘展示缓存；进程入口到可用模型，以及第一次 icon action 到可用数据帧分别计时 | App ready 后恢复 p95 ≤750 ms；另报完整 launch 时间，不把 hosted XCTest 的空 coordinator 当完整冷启动 |
| P03 | 已恢复 publication 内切换现有客户端/时段/面板 | p95 ≤100 ms；无 helper/扫描/OTel 等待 |
| P04 | 无展示缓存但已有完整已提交数据库；第一次准备可用数据 | p95 ≤2 s；与完全没有已存数据的首次导入分开 |
| P05 | 引擎已接收并持久化的可计量 OTel event 到新可见 publication | p95 ≤2 s；不含生产者未发送的时间，另报端到端 freshness |
| P06 | 空闲、无任务/无 OTel 流量，30 分钟 | 后台新增平均 CPU ≤单核 0.5%；新增后台稳定 RSS ≤64 MiB；≤1 次维护唤醒/分钟。有限 helper 应退出；另报 App 总量 |
| P07 | 重建中 aggregate engine + collector + 子进程资源 | RSS ≤256 MiB；前台 P01/P03 不回归；写事务 p95 ≤50 ms、max ≤250 ms |
| P08 | 规模 no-op 与一次 append | no-op 正文 decode=0；append bytes ≤delta + 每来源已声明的有限 anchors；第二次导入无重复 |
| P09 | ≥5,071 文件代表性 corpus 的全量重建 | 分阶段预算和 wall/CPU/bytes/RSS 全部报告；默认方案中位 wall 至少优于同输入基线 30%，且满足 P01/P07 |
| P10 | JSONL 的完整记录写入隔离来源，到打开的原生 popover 显示相应新数值 | 先验证记录已落盘；p95 ≤2 s，另报通知、排队、处理及发布；漏通知不得改记为自动成功 |
| P11 | 全新安装、空数据库、本机大规模既有日志；第一批今天用量到真实可读帧 | 独立报告来源选择/读取/统计/原生绘制及完整历史完成时间；当前代表性规模目标p95 ≤3 s，部分覆盖必须明示；今天相关输入扩大时重新评估，不外推1.55 s |

真正首次导入的首个“已采集部分”及全量完成时间必须测量和展示；由于无既有数据、
输入大小无上限，不承诺空状态下 200 ms 产生真实数字。P04 失败则不能交付为“快开已解决”；
先修复 bootstrap 或返回设计并重新评审，不能默默略去首次路径。

本设计的“首屏”专指真实 NSPopover 已打开，当前选择的客户端/时段/面板里，
有效用量或额度观察已完成原生绘制，可辨日期与完整性并能操作。
只有 loading、空卡片、窗口出现、coordinator 有值或扫描完成都不算。
浏览器原型用于文案和状态验收，浏览器 rAF 耗时不作产品性能证据。
日常点击、启动恢复、实时更新是同一体验的三种前置状态，必须各自与相同前置状态的基线比较。

若实现中证明某目标在既定 UX 与架构约束下不可达（例如原生控件自身的下限），
实现者停止并返回设计，由用户在“改 UX/架构”与“改目标”之间决定并经评审；
不得在实现、评审或验收阶段自行豁免。

## 正确性与完成边界

- 增量/分段/并行/全量结果按逻辑行、请求身份和完整输出差分比较，忽略声明过的时间戳等非语义差异。
- 生命周期、跨天/DST、时区、restore、升级、磁盘满、崩溃、App/CLI 并发和陌生协议均有回归。
- App 默认额度、所有数据面板及真实 icon 路径有 native 验收；浏览器标本只证明设计与状态。
- OTel-only 补采、跨来源去重和历史缺口有独立证据，不能凭 collector health 通过。
- 每个任务需独立实现评审和精确 content-state 的 CEv1 门禁 `VERIFIED`；
  Review PASS 不能替代未 VERIFIED 的门。提交、推送、PR、安装、发布另需用户授权；
  不改生产数据，测量只用隔离 state root 与生成夹具。

## 非目标

本主题不重构价格/credits，不决定辅助会话筛选或父子展示，不改模型设置或 Memories 开关，
不自动迁移日志根、不收集会话正文，不采用 CPA 数据，不换 SQLite driver，不默认引入 CGO，
不扩展 Linux/第三客户端，也不把延长 120 秒 timeout 当作性能方案。
